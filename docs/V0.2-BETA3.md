# v0.2.0-beta.3：字符集转换与字体注入

在原有工程上新增两个独立、默认关闭的模块。仍限 Windows x64 目标，不修改目标 EXE、磁盘文本、真实系统区域设置或全局字体安装。

## 使用

1. 选择目标 EXE，先退出旧实例。
2. 在「字符集 / 代码页」启用转换，分别选择 ANSI（含线程默认）和 OEM 代码页。日文旧程序通常使用 CP932；这不要求同时启用日语 UI 或 Locale。
3. 在「字体注入 / 替换」填写字体内部名称（例如 Meiryo），可指定要替换的原字体名称；留空原名称表示替换全部受支持的 GDI 创建请求。
4. 可选 TTF / OTF / TTC 文件；只加载私有字体时可留空替换名称。文件不会被安装到系统或复制进便携包，启动时需要原路径仍然存在。配置导出只包含路径。
5. 字体字符集默认为保留应用请求；日文可选 SHIFTJIS。这控制 GDI 字体匹配，不等于字节编码转换。
6. 启动并检查日志。私有资源加载为 INFO；实际发生的字体或转换 API 调用才记录为 HOOK。GDI 可对不存在或不匹配的字体进行回退，成功创建逻辑字体不代表一定使用指定物理字体。

旧 settings v1/v2 和旧导入文件自动补齐两个关闭的模块。现有日本预设保留原行为，不自动开启新模块。启用子进程 Hook 时，子进程独立继承本次启动配置并加载私有字体。

## API 范围

| 模块 | 范围 |
| --- | --- |
| 默认代码页 | `GetACP`、`GetOEMCP` |
| 默认转换 | `MultiByteToWideChar`、`WideCharToMultiByte` 的 `CP_ACP=0`、`CP_OEMCP=1`、`CP_THREAD_ACP=3` |
| 代码页属性 | `GetCPInfo`、`GetCPInfoExA/W`、`IsDBCSLeadByteEx` 的默认参数；`IsDBCSLeadByte` |
| GDI 字体 | `CreateFontA/W`、`CreateFontIndirectA/W`、`CreateFontIndirectExA/W` |
| 私有字体 | 在目标进程调用 `AddFontResourceExW(FR_PRIVATE)`；正常停止监控调用 `RemoveFontResourceExW` |

代码页预设：932、936、949、950、1252、437、850、65001。显式指定的编码（包括显式 CP932 或 UTF-8）不重写。转换由 Windows 原函数执行，保留原生缓冲区长度、非法序列处理、默认字符、返回值和错误码语义。

字体替换保留大小、粗细、倾斜等属性；LOGFONT 输入先复制再修改，不写入应用提供的结构。ANSI 字体请求转为 Unicode 创建，支持目标字体名称不在宿主 ANSI 代码页中的情况。字体名最多 31 个 UTF-16 单元。

字体文件无效时初始化失败并清理挂起目标，不带着失败的字体配置继续运行。清理可重复调用。正常退出启动器或停止监控时卸载私有字体；后端异常断开可能使进程私有字体保留至目标退出，Windows 会在进程退出时释放。已创建字体对象和应用自身缓存不会被强制重建。

## 技术边界

- 这不是完整的系统代码页虚拟化。CRT、应用自带编码库、缓存的 NLS 数据、直接内部调用、文件名 A 接口及控制台输入输出代码页等不保证覆盖。
- Locale 与代码页是独立配置；`GetLocaleInfo*` 的代码页元数据仍来自所选 Locale，本模块不改写该元数据。应用如果直接使用这些显式值转换，可能与独立代码页设置不同。
- GDI 字体替换不保证覆盖 DirectWrite、WPF、浏览器、游戏自绘文本、字体缓存和字体回退。私有 GDI 字体不保证被这些框架枚举或使用。
- 更换字体不能修复已错误解码的文字。代码页转换也不能给字体补充缺失字形。
- 未新增 x86 / ARM64 支持，未对用户目标软件的完整业务流程作兼容性承诺。
